# 构建原理

了解 Nexus-AI 是如何将你的自然语言需求转化为一个可运行的 AI Agent。

## 核心理念：Agent Build Agent

Nexus-AI 的核心架构是 **"用 AI Agent 来构建 AI Agent"**。平台内部有一支由 **8 个专业 Builder Agent** 组成的 AI 开发团队，外加一个 **Agent Deployer** 负责部署上线。它们通过严格定义的流水线协作，将你的自然语言需求自动转化为可运行的 Agent。

这就好比一个软件开发团队 —— 有项目经理统筹协调、产品经理分析需求、架构师设计方案、设计师定义交互、提示词专家编写指令、工具工程师开发功能、软件工程师编写代码、技术经理审查质量。只不过这个"团队"的所有成员都是 AI。

## 构建流水线总览

当你提交需求后，会经过以下 9 个阶段，每个阶段由专门的 Builder Agent 负责：

```
你的需求（自然语言 + 可选附件）
  ↓
┌─────────────────────────────────────────────────┐
│  ① 编排调度 (Orchestrator Agent)                 │
│     分析需求复杂度，制定构建计划，分配任务路由        │
│     产出：构建计划、任务分配方案                     │
├─────────────────────────────────────────────────┤
│  ② 需求分析 (Requirements Agent)                 │
│     解析需求，智能提问澄清细节，生成需求规格          │
│     产出：结构化需求文档                            │
├─────────────────────────────────────────────────┤
│  ③ 系统架构 (Architecture Agent)                 │
│     设计技术架构，规划组件和集成方案                  │
│     产出：架构设计文档、技术选型方案                  │
├─────────────────────────────────────────────────┤
│  ④ Agent 设计 (Design Agent)                     │
│     定义行为模式、交互流程、错误处理策略              │
│     产出：行为设计文档、交互流程定义                  │
├─────────────────────────────────────────────────┤
│  ⑤ 提示词工程 (Prompt Agent)                     │
│     编写系统提示词，优化指令，定义角色人设             │
│     产出：YAML 格式系统提示词文件                    │
├─────────────────────────────────────────────────┤
│  ⑥ 工具开发 (Tools Agent)                        │
│     开发工具函数，集成 API，编写测试                 │
│     产出：Python 工具函数代码                       │
├─────────────────────────────────────────────────┤
│  ⑦ 代码开发 (Developer Agent)                    │
│     编写 Agent 主程序，整合所有模块                  │
│     产出：Agent 主程序 Python 代码                  │
├─────────────────────────────────────────────────┤
│  ⑧ 开发管理 (DevManager Agent)                   │
│     代码审查，质量验证，集成测试                     │
│     产出：审查报告、质量验证结果                     │
├─────────────────────────────────────────────────┤
│  ⑨ 部署上线 (Agent Deployer)                     │
│     部署 Agent 并使其可以被调用                     │
│     产出：可运行的 Agent 实例                       │
└─────────────────────────────────────────────────┘
  ↓
可对话的 AI Agent ✅
```

## 各阶段详细说明

### 阶段 1：编排调度 (Orchestrator Agent)

**角色类比：** 项目经理

**核心职责：**

Orchestrator 是整个构建流水线的"大脑"和"总指挥"。当你提交需求后，它首先接管任务：

- **需求复杂度分析** — 评估需求的规模、难度和所需资源
- **构建计划制定** — 根据分析结果，规划各阶段的执行顺序和资源分配
- **任务路由** — 将构建任务依次路由到各个专业 Builder Agent
- **依赖关系解析** — 确保各阶段之间的依赖关系正确处理
- **进度跟踪** — 监控整个构建流水线的执行进度

**产出物：** 构建计划文档、任务分配和路由方案

::: tip 为什么需要编排调度？
不同复杂度的需求，构建策略也不同。简单的 Agent 可能只需要基本的提示词和少量工具，复杂的 Agent 则需要更精细的架构设计和大量定制工具。Orchestrator 的作用就是确保每个构建任务都能获得最合适的处理方案。
:::

---

### 阶段 2：需求分析 (Requirements Agent)

**角色类比：** 产品经理

**核心职责：**

Requirements Agent 负责将你的自然语言描述转化为准确、完整的结构化需求文档：

- **需求解析** — 分析你的描述，提取核心功能需求
- **智能澄清** — 识别需求中的模糊点和遗漏项，通过提问获取补充信息
- **需求规格化** — 将需求整理为结构化的规格文档，包含：
  - Agent 的目标定位和使用场景
  - 具体功能清单和优先级
  - 输入/输出格式定义
  - 工具和集成需求
  - 约束条件和行为边界
- **需求验证** — 确认需求的可行性和完整性

**产出物：** 结构化需求文档（包含功能列表、输入输出定义、约束条件等）

**用户交互点：** 在「引导创建」模式下，这个阶段会通过多轮问答与你互动。例如：
- "你提到需要数据分析功能，具体需要哪些分析方法？统计分析、趋势分析、还是预测分析？"
- "Agent 需要支持哪些数据格式？CSV、Excel、JSON？"
- "分析结果需要以什么形式呈现？文字报告、表格、还是可视化图表？"

---

### 阶段 3：系统架构 (Architecture Agent)

**角色类比：** 系统架构师

**核心职责：**

Architecture Agent 根据需求文档设计 Agent 的技术架构方案：

- **架构设计** — 确定 Agent 的整体技术架构
- **组件规划** — 规划 Agent 需要哪些组件（模型、工具、中间件等）
- **集成映射** — 确定需要集成的外部服务和 API
- **技术选型** — 选择最适合的模型配置、工具框架等
- **性能规划** — 评估资源需求和性能预期

**产出物：** 架构设计文档、组件规划图、技术选型方案

**示例：** 对于"医学文献研究助手"这个需求，Architecture Agent 可能会设计：
- 使用 Claude 模型处理自然语言理解和生成
- 需要 PubMed API 搜索工具
- 需要 PDF 解析工具
- 需要引用格式化工具
- 需要文献数据缓存机制

---

### 阶段 4：Agent 设计 (Design Agent)

**角色类比：** 交互设计师

**核心职责：**

Design Agent 负责定义 Agent 的"性格"和"行为方式"：

- **行为模式设计** — 定义 Agent 在不同场景下的行为逻辑
- **交互流程设计** — 设计用户与 Agent 的对话流程
- **错误处理策略** — 定义当出现异常情况时 Agent 的应对方式
- **响应风格定义** — 确定 Agent 的回复风格（专业、友好、简洁等）
- **边界行为定义** — 明确 Agent 不应该做什么，防止越界

**产出物：** 行为设计文档、交互流程定义、响应模板

**示例：** 对于客服 Agent，Design Agent 会定义：
- 用户问候时 → 友好回应并主动询问需求
- 用户提出问题时 → 先理解问题再在知识库中搜索答案
- 无法回答时 → 坦诚告知并建议联系人工客服
- 用户不满时 → 表达理解和歉意，升级处理

---

### 阶段 5：提示词工程 (Prompt Agent)

**角色类比：** 提示词专家

**核心职责：**

Prompt Agent 是影响 Agent 质量的关键角色，负责编写让 AI 模型准确理解角色和任务的提示词：

- **系统提示词编写** — 编写精确的系统级提示词（System Prompt）
- **指令优化** — 确保指令清晰、无歧义、易于模型理解
- **角色人设定义** — 定义 Agent 的身份、专业领域、语言风格
- **能力边界说明** — 明确告诉模型它能做什么、不能做什么
- **工具使用指引** — 在提示词中说明何时以及如何调用各个工具
- **输出格式规范** — 定义响应的格式和结构要求

**产出物：** YAML 格式的系统提示词文件

**提示词质量的重要性：** 提示词的好坏直接决定了 Agent 的表现。一个好的提示词就像是给 AI 的"岗位说明书" —— 越详细、越准确，Agent 的表现就越好。

---

### 阶段 6：工具开发 (Tools Agent)

**角色类比：** 工具开发工程师

**核心职责：**

Tools Agent 负责开发 Agent 需要的所有工具函数。工具是 Agent 与外部世界交互的"手脚"：

- **工具函数开发** — 根据架构方案，编写 Python 工具函数
- **API 集成** — 对接外部 API 和服务
- **参数定义** — 为每个工具定义清晰的输入参数和返回值
- **功能测试** — 确保每个工具函数能正确执行
- **文档编写** — 为工具编写使用说明

**产出物：** Python 工具函数代码及文档

**工具示例：**
- 文件操作工具（读取 CSV、解析 Excel、写入文件）
- API 调用工具（HTTP 请求、搜索 API、数据查询）
- 数据处理工具（统计计算、格式转换、数据清洗）
- 代码执行工具（运行 Python 代码、Shell 命令）

---

### 阶段 7：代码开发 (Developer Agent)

**角色类比：** 软件工程师

**核心职责：**

Developer Agent 负责编写 Agent 的主程序代码，将前面阶段的所有产出整合为一个可运行的程序：

- **主程序编写** — 编写 Agent 的核心 Python 代码
- **模块整合** — 将提示词、工具函数、业务逻辑组装在一起
- **接口实现** — 实现 Agent 的对话接口和文件处理接口
- **配置管理** — 处理 Agent 的配置和初始化逻辑
- **基础测试** — 编写并执行基础功能测试

**产出物：** Agent 主程序 Python 文件

---

### 阶段 8：开发管理 (DevManager Agent)

**角色类比：** 技术经理 / 代码审查员

**核心职责：**

DevManager Agent 是构建质量的最后一道把关人：

- **代码审查** — 逐行审查 Agent 代码和工具代码
- **质量保证** — 检查代码是否符合编码规范和最佳实践
- **安全检查** — 排查潜在的安全隐患（如注入攻击、数据泄露等）
- **集成测试** — 验证各组件之间的协作是否正确
- **性能评估** — 评估 Agent 的响应性能
- **问题修复** — 发现问题后协调 Developer Agent 进行修复

**产出物：** 代码审查报告、质量验证结果

::: info
DevManager Agent 的审查可能会触发代码修改。如果发现严重问题，它会要求 Developer Agent 重新修改代码，确保最终交付的 Agent 质量达标。
:::

---

### 阶段 9：部署上线 (Agent Deployer)

**角色类比：** 运维工程师

**核心职责：**

Agent Deployer 是流水线的最后一个阶段，负责将构建好的 Agent 部署并使其可用：

- **环境准备** — 配置运行环境、依赖安装
- **Agent 注册** — 将 Agent 注册到平台中
- **部署执行** — 支持两种部署方式：
  - **本地部署 (Local)** — 直接在 Nexus-AI 服务器上运行
  - **云端部署 (AgentCore)** — 部署到 AWS Bedrock AgentCore 云端托管
- **可用性验证** — 确认 Agent 可以正常接受请求和响应
- **状态激活** — 将 Agent 状态设置为"运行中"

**产出物：** 已部署的、可正常使用的 Agent 实例

## 构建过程中的状态流转

构建任务在执行过程中可能处于以下状态：

```
          ┌──────────┐
          │  Pending  │  等待开始
          │  (待处理)  │
          └────┬─────┘
               ↓
          ┌──────────┐
    ┌─────│ Running   │  正在执行
    │     │ (运行中)   │
    │     └────┬─────┘
    │          │
    │     ┌────┴─────────────────┐
    │     ↓                      ↓
    │ ┌──────────┐        ┌──────────┐
    │ │Completed │        │  Failed  │  执行失败
    │ │ (已完成)  │        │  (失败)   │
    │ └──────────┘        └──────────┘
    │
    ├────→┌──────────┐
    │     │ Paused   │  人工暂停
    │     │ (已暂停)  │
    │     └──────────┘
    │
    └────→┌──────────────┐
          │Waiting Human │  等待人工确认
          │(等待人工确认)  │
          └──────────────┘
```

| 状态 | 说明 |
|------|------|
| **Pending（待处理）** | 构建任务已创建，等待执行 |
| **Running（运行中）** | 正在执行构建流水线 |
| **Waiting Human（等待人工确认）** | 在引导创建中，等待用户回答问题或确认需求 |
| **Completed（已完成）** | 所有阶段成功完成，Agent 已可用 |
| **Failed（失败）** | 某个阶段执行失败 |
| **Paused（已暂停）** | 用户手动暂停了构建任务 |

## 构建产物一览

一次成功的构建会产生以下产物，所有产物都可以在 [项目管理](/using/projects) 页面中查看：

| 产物 | 格式 | 说明 |
|------|------|------|
| **Agent 主程序** | Python (.py) | Agent 的核心代码文件，包含主逻辑 |
| **工具函数** | Python (.py) | Agent 调用的各个工具函数代码 |
| **系统提示词** | YAML (.yaml) | 定义 Agent 角色和行为的提示词文件 |
| **需求文档** | 结构化文本 | 由 Requirements Agent 生成的需求规格 |
| **架构文档** | 结构化文本 | 由 Architecture Agent 生成的架构方案 |
| **设计文档** | 结构化文本 | 由 Design Agent 生成的行为设计方案 |
| **审查报告** | 结构化文本 | 由 DevManager Agent 生成的质量报告 |

## 真实案例：医学文献研究助手

让我们用一个真实案例，展示构建流水线每个阶段具体做了什么：

**用户需求：** "创建一个医学文献研究助手，能在 PubMed 上搜索论文、解析 PDF 全文、提取关键数据，并按 APA 格式生成引用。"

| 阶段 | 具体工作 | 产出 |
|------|----------|------|
| ① 编排调度 | 判断为中等复杂度，需要 API 集成和文件处理能力 | 构建计划：需要开发 3 个自定义工具 |
| ② 需求分析 | 明确搜索范围（PubMed）、输出格式（APA）、支持语言（中英文） | 需求规格：6 项核心功能 |
| ③ 系统架构 | 设计三层工具架构：搜索层 → 解析层 → 输出层 | 架构图、API 选型 |
| ④ Agent 设计 | 定义对话流程：主题输入 → 论文搜索 → 结果筛选 → 深入分析 → 生成引用 | 交互流程和响应模板 |
| ⑤ 提示词工程 | 编写系统提示词，定义"医学研究助手"角色，指定学术写作风格 | YAML 提示词文件 |
| ⑥ 工具开发 | 开发 `search_pubmed()`、`parse_pdf()`、`format_citation()` 三个工具 | 3 个 Python 工具函数 |
| ⑦ 代码开发 | 编写 Agent 主程序，整合提示词和工具 | Agent Python 代码 |
| ⑧ 开发管理 | 审查代码质量、测试 API 调用、验证引用格式正确性 | 审查通过 |
| ⑨ 部署上线 | 部署到本地环境，激活 Agent | 可用的 Agent ✅ |

## 多 Agent 协作机制

### 层级化团队架构

Builder Agent 之间并不是简单的线性传递，而是组成了一个 **层级化的协作团队**，不同角色处于不同的职责层级：

```
用户需求输入
  ↓
┌─ Function Agent Level ──────────────────────────────────┐
│  意图识别 Agent（Supervisor）                             │
│  → 识别用户意图，创建构建任务                              │
└─────────────────────────────────────────────────────────┘
  ↓
┌─ Team Level ────────────────────────────────────────────┐
│  需求分析团队                                            │
│  ├─ Expert Level: 需求深度理解专家                        │
│  │   ├─ 需求分析专家                                     │
│  │   └─ 产品测试用例专家                                  │
│  └─ Team Level: 研发设计团队                              │
│       ├─ Specialist: Agent 应用架构师                     │
│       ├─ Specialist: Agent 设计师                        │
│       └─ Team Level: Agent 开发团队                      │
│            └─ Execution Level: 项目交付经理               │
│                 ├─ 工具开发工程师                          │
│                 ├─ 提示词工程师                            │
│                 ├─ Agent 开发工程师                        │
│                 └─ 内容审查工程师                          │
└─────────────────────────────────────────────────────────┘
  ↓
┌─ Function Agent Level ──────────────────────────────────┐
│  智能资产复用推荐                                         │
│  → Agent 库索引、工具库索引、提示词库索引                   │
└─────────────────────────────────────────────────────────┘
  ↓
┌─ Engineer Level ────────────────────────────────────────┐
│  测试工程师                                              │
└─────────────────────────────────────────────────────────┘
  ↓
完整可运行项目 ✅
```

### 智能资产复用

构建过程中，系统会自动检查已有的 **智能资产库（AgentBase）**，复用已有资源以加速构建：

| 资产类型 | 复用方式 |
|----------|----------|
| **Agent 库索引** | 检索已有的同类 Agent 作为参考模板 |
| **工具库索引** | 复用已开发的工具函数，避免重复开发 |
| **提示词库索引** | 参考已验证的高质量提示词模板 |
| **内置模板** | 使用预置的 Agent、工具、提示词模板 |

这意味着平台使用越久，积累的资产越多，新 Agent 的构建速度就越快、质量就越高。

### 阶段间协作

每个 Agent 的产出会作为下一个 Agent 的输入，通过 **异步消息队列** 传递：

```
Orchestrator → [构建计划] → Requirements Agent
Requirements Agent → [需求文档] → Architecture Agent
Architecture Agent → [架构方案] → Design Agent
Design Agent → [设计文档] → Prompt Agent
Prompt Agent → [提示词] → Tools Agent
Tools Agent → [工具代码] → Developer Agent
Developer Agent → [Agent 代码] → DevManager Agent
DevManager Agent → [审查通过] → Agent Deployer
```

每个 Agent 的工作成果（构建产物）都保存在云端存储中，确保构建过程可追溯、可回放。你可以在 [构建进度](/using/build-progress) 页面查看每个阶段的详细产出。

## 项目产出目录结构

每个构建完成的项目都有一个标准化的目录结构：

```
projects/
└── your_agent_project/
    ├── README.md                          # 项目说明文档
    ├── config.yaml                        # 项目配置文件
    ├── status.yaml                        # 项目状态文件
    ├── workflow_summary_report.md          # 工作流总结报告
    ├── agents/
    │   ├── requirements_analyzer.json     # 需求分析文档
    │   ├── system_architect.json          # 系统架构设计文档
    │   ├── agent_designer.json            # Agent 设计文档
    │   ├── tools_developer.json           # 工具开发文档
    │   ├── prompt_engineer.json           # 提示词工程文档
    │   ├── agent_code_developer.json      # Agent 代码开发文档
    │   └── agent_developer_manager.json   # 开发管理总结文档
    ├── tools/
    │   └── generated_tools/
    │       └── your_agent/
    │           └── your_tool.py           # 自动生成的工具函数
    ├── prompts/
    │   └── generated_agents_prompts/
    │       └── your_agent/
    │           └── your_agent.yaml        # 自动生成的提示词
    └── agents/
        └── generated_agents/
            └── your_agent/
                └── your_agent.py          # 自动生成的 Agent 代码
```

## Token 消耗分布

各阶段的 Token 消耗占比并不均等，以下是实际测试数据中的平均分布：

| 阶段 | Token 消耗 | 占比 | 说明 |
|------|-----------|------|------|
| 编排调度 (Orchestrator) | 59K | 5.6% | 主要是分析和规划，消耗最少 |
| 需求分析 (Requirements) | 64K | 6.1% | 需求解析和规格化 |
| 系统架构 (Architecture) | 200K | 19.0% | 架构设计需要考虑较多因素 |
| Agent 设计 (Design) | 281K | 26.7% | 行为设计复杂度较高 |
| 开发管理 (DevManager) | 448K | 42.6% | 包含代码审查、测试和修复，消耗最大 |

::: tip
开发管理阶段消耗最多的 Token，因为它不仅要审查代码，还可能触发代码修复和重新测试的循环，确保最终交付质量。
:::

## 关键技术指标

在构建过程中，平台会追踪以下关键指标：

| 指标 | 说明 |
|------|------|
| **总耗时** | 从提交需求到 Agent 可用的总时间 |
| **输入 Tokens** | 所有 Builder Agent 消耗的输入 Token 总量 |
| **输出 Tokens** | 所有 Builder Agent 生成的输出 Token 总量 |
| **工具调用次数** | Builder Agent 在构建过程中调用工具的总次数 |
| **各阶段耗时** | 每个阶段的独立执行时间 |

这些指标可以在构建进度页面实时查看，帮助你了解构建的资源消耗情况。
