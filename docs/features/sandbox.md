# Sandbox 沙箱

## 这是什么

Sandbox 是 Nexus-AI 里每一次 Agent 对话真正执行的地方。平台默认把 Agent 放进一台独立的 Firecracker microVM 里跑，和其他用户、其他 Agent、甚至平台自身的后端都彻底隔开；你看到的工作空间文件、模型调用、工具执行全部发生在这台「一人一间」的小机器里。对话结束后 VM 不会立刻销毁，而是回到空闲池等下次复用——这样既安全又不会让你每次发消息都等冷启动。

## 使用场景

| 场景 | Sandbox 帮你做什么 |
| --- | --- |
| 运行会读文件、写文件或执行代码的 Agent | 把执行过程关进 microVM，工作空间和凭证都不会泄漏到其他用户 |
| 同一个会话连续对话 | 下一条消息优先命中上一次的 VM，工作空间已挂载，无需重新准备 |
| 开了一个绑定了多个生成工具的 Agent | 第一次运行时自动为该 Agent 装依赖，第二次开始秒启 |
| 管理员需要切换隔离级别 | 可从「本地直跑（无隔离）」切到「Firecracker 沙箱」，并决定是否允许用户覆盖 |
| 运维想控制成本 | 节点空闲一段时间会自动缩容；流量来了又会自动拉起新节点 |

## 如何使用

### 场景一：作为普通用户发起对话

<!-- SCREENSHOT: sandbox-chat-running -->

你什么都不用改。一条消息从聊天窗口发出后，平台会：

1. 按当前运行时策略选择执行位置（默认是 Firecracker 沙箱）。
2. 从空闲池挑一台可复用的 VM，或在有空闲资源的节点上拉起一台新 VM。
3. 把工作空间（共享数据卷里属于你的目录）挂进 VM，VM 里启动 Agent。
4. Agent 的输出通过流式通道回传到前端，你会先看到「Preparing sandbox environment…」提示，然后开始出字。
5. 对话结束后 VM 回到空闲池，下次你或同一会话继续对话时优先复用它。

::: tip 为什么第一条消息稍慢
如果没有可复用的 VM，平台需要冷启动一台新 VM；如果连节点都没有空余，会再启动一台 EC2 节点，这一步通常需要 1–5 分钟。后续对话都会复用已有 VM，秒级返回。
:::

### 场景二：管理员切换运行时模式

<!-- SCREENSHOT: sandbox-runtime-policy -->

在「系统设置 → 沙箱运行时」中可以选择：

1. **默认运行时**（`default_runtime`）
   - `local` — 后端服务节点直接执行，无隔离，适合开发/调试。
   - `ec2` — Firecracker microVM 隔离执行（生产推荐，默认值）。
   - `agentcore` — AWS Bedrock AgentCore 托管执行（暂未开放）。
2. **允许的运行时集合**（`allowed_runtimes`）：勾选平台允许使用的模式。
3. **是否允许用户覆盖**（`allow_user_override`）：关闭则所有 Agent 一律走默认运行时；开启则前端可按 Agent 切换。
4. 保存后，新发起的对话会按新策略调度；已经在跑的对话不受影响。

::: warning 切换到 `local` 的影响
`local` 模式跳过所有 microVM 隔离，Agent 直接在后端服务节点上执行。仅用于开发/测试环境；生产环境请保持 `ec2`。切换为 `local` 后，平台会缩短空闲节点等待时间并在巡检中释放现有 EC2 节点，避免留下无用资源。
:::

### 场景三：管理员查看沙箱集群状态

<!-- SCREENSHOT: sandbox-cluster-status -->

平台自带一个 Sandbox 控制器（独立后台服务），它每隔 30 秒巡检一次，并对外提供 HTTP 接口：

1. `GET /health` — 控制器本身是否存活。
2. `GET /status` — 最近一次巡检结果：在线节点数、运行中 VM 数、空闲节点数、本轮是否发生了扩缩容。
3. `POST /scale_down` — 手动触发缩容，可传 `min_nodes`（保留节点下限）和 `dry_run`（只列出候选，不真缩）。

你也可以通过命令行启动控制器：

```bash
nexus-cli service start --sandbox-controller
```

### 场景四：节点自动扩缩容

巡检会自动处理以下情况，一般你不需要手动干预：

1. **节点心跳超时** → 标记为 offline，释放其上的幽灵 VM 记录。
2. **所有节点都满载** → 自动启动新 EC2 节点，直到达到 `max_size`。
3. **节点持续空闲超过阈值** → 依次停止节点上的沙箱服务、卸载共享存储、终止 EC2 实例、清理登记表（保留至少 `min_nodes` 个节点）。
4. **运行时切到 `local`** → 允许把所有 EC2 节点释放干净（`min_nodes` 临时降为 0）。

### 场景五：定制 VM 规格与节点池

<!-- SCREENSHOT: sandbox-pool-config -->

在「沙箱节点池」配置页可以调整：

1. **节点实例类型**（例如 `c8i.xlarge`、`m8i.2xlarge`、`r8i.4xlarge` 等）。
2. **每台 VM 的 vCPU / 内存**（默认 1 vCPU、768 MiB）。
3. **节点池下限 / 上限 / 期望值**（`min_size` / `max_size` / `desired_size`）。
4. **每节点最大 VM 数**（填 `auto` 由平台按实例规格自动计算）。
5. **预热策略**：是否为「精选 Agent」预热、保留多少台空闲 VM 等待请求。

## 关键参数 / 限制

| 参数 | 说明 | 默认值 |
| --- | --- | --- |
| 默认运行时 | 新对话的默认执行位置 | `ec2` |
| 允许的运行时 | 允许平台选择的运行时集合 | `local`, `ec2` |
| 允许用户覆盖运行时 | 用户/Agent 是否可以指定非默认运行时 | 关闭 |
| 单次调用超时 | 一次 Agent 执行的最长时长 | 600 秒 |
| 每 VM vCPU | 分给每台 microVM 的 vCPU 数 | 1 |
| 每 VM 内存 | 分给每台 microVM 的内存 | 768 MiB |
| 每 VM vCPU 配额 | 容量计算时的 vCPU 占用（支持小数做超分） | 0.5 |
| VM 启动超时 | VM 起不来多久算失败 | 30 秒 |
| VM 空闲回收 | 空闲 VM 多久未使用会被销毁 | 300 秒 |
| 节点空闲缩容阈值 | 节点持续空闲多久后触发缩容 | 10 分钟 |
| 节点池最小节点数 | 即使空闲也保留的节点数 | 1 |
| 最大并发 VM 数 | 整个平台同时运行的 microVM 上限 | 50 |
| 心跳超时 | 节点多久不心跳就标记为 offline | 90 秒 |
| 巡检间隔 | 控制器两次巡检之间的间隔 | 30 秒 |

| 限制 | 细节 |
| --- | --- |
| 必须支持嵌套虚拟化 | 节点 EC2 实例必须是支持 KVM 的第 8 代 Intel 实例（`c8i`、`m8i`、`r8i`，不含 `d` 后缀变体）或任意 `.metal` 实例 |
| 不支持的实例 | 6/7 系列普通实例、带 NVMe 的 `c8id`/`m8id`/`r8id`、ARM/AMD 实例均无法承载 Firecracker |
| 网络 | 每节点一个 Linux bridge，默认网段 `172.16.0.0/24`；VM 通过 NAT 出公网；反向代理端口范围 `18001–18100` |
| 共享存储 | 每个节点必须挂载两套共享文件系统：只读代码卷（平台代码）+ 可读写数据卷（工作空间、Agent 虚拟环境、事件） |
| 工作空间同步 | Agent 执行完成后，工作空间会增量同步到 S3 会话存储桶；没配置 S3 桶则仅保留在共享数据卷 |
| 模板挂载 | 单次会话最多挂 30 个模板资源包；按 `mount_name` 隔离，多会话并发安全 |
| 凭证 | VM 内没有 IMDS，AWS 临时凭证由主节点凭证代理下发，过期前约 30 分钟自动刷新 |
| 依赖安装 | 首次为某个 Agent 起 VM 时，会根据其绑定工具的 `requirements.txt` 懒加载依赖；失败不会中断对话，只会标记后续跳过 |
| agentcore 模式 | 目前仅为占位，实际不可用；请保持默认或选择 `ec2` |
| 冷启动时长 | 有空闲节点时约数秒；需要新拉节点时通常 1–5 分钟，具体取决于 EC2 启动速度 |

## 常见问题

**Q1：我关掉浏览器再回来，同一个会话还能接着跑吗？**
A：可以。Sandbox 会记住上次服务该会话的 VM，下次发消息时优先调度到那台（称为 Session 亲和），工作空间已挂载、上下文已在，几乎没有准备开销。如果那台 VM 已经被回收，平台会重新挑一台，依然能继续会话。

**Q2：为什么我发第一条消息时出现「Sandbox unavailable」？**
A：一般是所有节点都已满载，且正在启动新节点的过程中。稍等一会再发送即可；如果持续报错，请让管理员检查节点池 `max_size` 是不是设得太低、或 EC2 实例类型不支持嵌套虚拟化（见上方限制）。

**Q3：Agent 执行超过 600 秒会发生什么？**
A：超时后平台会返回 `Execution timed out after 600s` 错误、结束这次调用，并把占用的 VM 标记为失败（下次巡检时会被销毁重建）。长任务可以拆成多轮对话，或由管理员在沙箱设置里调大 `invocation_timeout`。

**Q4：我删了一个 Agent，它之前占用的依赖还会留在 VM 里吗？**
A：不会长期留着。每个 Agent 都有独立的虚拟环境目录，保存在共享数据卷上，由 Agent ID 作 key；Agent 被删除时其虚拟环境目录会被一起清理，其他 Agent 的 VM 不受影响。

**Q5：我是管理员，想强制立刻回收所有空闲节点，能做到吗？**
A：可以调用控制器的 `POST /scale_down` 接口，并把 `min_nodes` 显式设为 0；或者先在沙箱策略里把默认运行时切到 `local`，下一轮巡检就会把所有 EC2 节点释放掉。想先看看会影响哪些节点，可以加 `dry_run: true` 预览候选列表。
